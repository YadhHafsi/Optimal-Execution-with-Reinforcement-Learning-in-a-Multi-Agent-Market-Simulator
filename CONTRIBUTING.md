# Contributing

Thank you for your interest in this repository. It is the reproducibility code
of

> Y. Hafsi and E. Vittori, "Optimal Execution with Reinforcement Learning in a
> Multi-Agent Market Simulator", ACDSA 2026, DOI 10.1109/ACDSA67686.2026.11467851
> (arXiv:2411.06389).

Its primary purpose is to let anyone re-run the experiments of the paper and
verify the reported numbers. Contributions that improve reproducibility,
performance, documentation and test coverage are welcome. Contributions that
change the Markov decision process, the background market or the evaluation
protocol are welcome too, but they must be documented as described in
[Changes to the MDP](#changes-to-the-mdp) so that results stay comparable with
the paper.

The design is in `docs/DESIGN.md` and the changes to the original code, with the
bug and decision identifiers (B1-B12, D1-D16), in `docs/CHANGES.md`.

## Setting up a development environment

The project targets Python 3.10 and pins its dependencies (ray[rllib] 2.2.0,
gym 0.23.1, torch 1.13.1, numpy 1.23.5, pandas 1.5.3). We use
[uv](https://github.com/astral-sh/uv) to manage the virtual environment;
plain `python -m venv` and `pip` work as well.

```bash
git clone https://github.com/YadhHafsi/Optimal-Execution-with-Reinforcement-Learning-in-a-Multi-Agent-Market-Simulator
cd Optimal-Execution-with-Reinforcement-Learning-in-a-Multi-Agent-Market-Simulator

# create .venv and install everything (equivalent to `make install`)
uv venv --python 3.10 .venv
uv pip install --python .venv/bin/python -r requirements.txt \
    -e ./abides-core -e ./abides-markets -e ./abides-gym

source .venv/bin/activate
```

The repository contains three pip packages installed in editable mode:

| package | path | content |
|---|---|---|
| `abides-core` | `abides-core/` | discrete-event kernel, messages, latency models, generators |
| `abides-markets` | `abides-markets/` | exchange, order book, background trading agents, RMSC configurations, oracles |
| `abides-gym` | `abides-gym/` | Gym wrapper of the kernel and the execution environment `markets-execution-v0` |

The `experiments/` package (training, evaluation, figures) is not installed; it
is imported from the repository root (`python -m experiments.<script>`), which
is why every command below is run from the root.

`requirements.txt` is regenerated by the maintainer from the working
environment; please do not edit it by hand. If you need a new dependency,
mention it in the pull request and the maintainer will pin it.

On Linux and macOS set `OMP_NUM_THREADS=1` when running several trainings in
parallel; the `Makefile` does this for you.

## Running the tests

```bash
python -m pytest tests -q            # full suite, about 5 s
python -m pytest tests -q -m 'not slow'
make test                            # same as the first command
make test-fast                       # same as the second
```

`pytest.ini` also lists `abides-core/tests` and `abides-markets/tests` in
`testpaths`, so `python -m pytest -q` from the root runs the upstream ABIDES
tests as well (slower).

Tests that run a full, short ABIDES simulation are marked with
`@pytest.mark.slow`. Use the marker for any new test that builds a kernel and
steps the market; pure unit tests (reward formula, action mapping, policy
schedules, order-size model) must stay unmarked so that `test-fast` remains
fast. New tests go into `tests/` (top-level) when they concern the execution
environment or the experiments package, and into the `tests/` directory of the
relevant ABIDES sub-package when they concern the simulator.

Before opening a pull request the full suite must pass, and the CI workflow
(`.github/workflows/ci.yml`) additionally runs a smoke training:

```bash
python -m experiments.train_dqn --config experiments/configs/smoke.yaml \
    --lr 1e-3 --seed 10 --total-timesteps 1500 --out /tmp/smoke
```

## Coding conventions

The conventions below are the ones of the upstream ABIDES project, kept for the
new code as well (see `DEVELOPER-GUIDE.md` for examples).

* Formatting compatible with [black](https://black.readthedocs.io/) (default
  settings). Line length is not enforced strictly in the experiments package
  but keep lines readable.
* Imports sorted with [isort](https://pypi.org/project/isort/) (black profile).
* Type hints on every function signature and public class attribute. The
  `mypy.ini` in the root ignores missing stubs for numpy, pandas and scipy.
* Google-style docstrings for every public module, class and function
  (`Arguments:`, `Returns:`, `Attributes:` sections). Module docstrings of the
  experiments scripts double as their `--help` text, so keep them accurate.
* Physical quantities: prices in cents (ABIDES convention), times as
  nanosecond integers from `abides_core.utils.str_to_ns`, durations in
  `"HH:MM:SS"` strings in configuration files. Metric units elsewhere.
* No em-dashes in documentation and comments.
* Do not use `print` for diagnostics in library code; the experiments scripts
  print progress lines with `flush=True` because they are run in the background
  with output redirected to `logs/`.
* Keep the environment free of RLlib and torch imports. `experiments/policies.py`
  imports them lazily inside `RLlibDQNPolicy` so that the baselines can run in
  a plain multiprocessing pool.
* Reproducibility: every source of randomness must be seeded through the
  environment (`env.seed`) or the policy (`BasePolicy.reset(seed)`). Do not
  call `np.random.*` on the global state.

## Adding a new experiment configuration

Experiment configurations live in `experiments/configs/*.yaml` and are loaded by
`experiments.common.load_config`. The file name (without extension) is the
default `name` of the configuration and the default results directory
`results/<name>/`. A configuration has four sections:

```yaml
name: my_experiment

environment:      # forwarded verbatim to SubGymMarketsExecutionEnv_v0
  background_config: rmsc04
  timestep_duration: "1s"
  first_interval: "00:05:00"
  parent_order_size: 20000
  execution_window: "00:30:00"
  direction: BUY
  q_min: 20
  num_action_levels: 4
  depth_penalty_alpha: 2.0
  beta_not_enough: 5.0
  beta_too_much: 5.0
  is_weight: 1.0
  # plus mkt_close, starting_cash, state_history_length, market_data_buffer_length

background:       # forwarded to abides_markets.configs.rmsc04.build_config
  num_noise_agents: 1000
  num_value_agents: 102
  num_momentum_agents: 12
  mm_wake_up_freq: "60S"

training:         # read by experiments.train_dqn and experiments.make_figures
  algorithm: DQN
  seed: 10
  learning_rates: [1.0e-2, 1.0e-3, 1.0e-4]
  selected_learning_rate: 1.0e-3
  total_timesteps: 100000
  lr_decay_steps: 90000
  epsilon_timesteps: 10000
  final_epsilon: 0.02
  gamma: 0.9999
  hiddens: [50, 20]

evaluation:       # read by experiments.evaluate and experiments.make_figures
  policies: [RL, TWAP, Passive, Random]
  num_seeds: 50
  plot_seeds: 20
  seed_offset: 1000
  scenarios:      # name -> overrides of the background section
    standard: {}
    noise_10: {num_noise_agents: 10}
```

* Only the keys listed in `experiments.common.ENV_KEYS` are forwarded from
  `environment`; if you add a constructor argument to the environment, add its
  key there too.
* `evaluation.scenarios` maps a scenario name to a dictionary of overrides of
  the `background` section. Each scenario becomes a sub-directory of the
  results directory. The empty dictionary is the standard scenario.
* Evaluation seeds are `seed_offset + i`; keep them disjoint from
  `training.seed` (decision D10 in `docs/CHANGES.md`).
* Start from `paper.yaml` (the paper's setting) or `smoke.yaml` (tiny setting
  used by the tests and CI). If your configuration is meant to reproduce a
  table or figure of the paper, say which one in the header comment.

## Adding a policy

Execution policies live in `experiments/policies.py`. To add one:

1. Subclass `BasePolicy` and implement `get_action(self, state) -> int` on the
   action grid of the environment (`0` = do nothing, `k` = market order of
   `k * q_min` shares). Set the class attribute `name`; it is the value written
   in the `policy` column of the results files.
2. Use `self.rng` (a `numpy.random.RandomState`) for any randomness and
   override `reset(seed)` if the policy keeps state between steps (see
   `TWAPPolicy`).
3. Optionally implement `q_values(state)` if the policy has action values to
   plot (Figure 6c).
4. Register the policy in `make_policy` (same file). The factory receives
   `env_params` with `parent_order_size`, `q_min`, `num_action_levels`,
   `num_steps` and `env_config`; the name comparison is case-insensitive.
5. Keep the policy free of RLlib and torch imports unless it wraps a trained
   model; in that case import them lazily inside `__init__`, as
   `RLlibDQNPolicy` does, so that the baselines still run in worker processes.
6. Add a unit test in `tests/test_policies_and_models.py` (action frequencies,
   schedule, reproducibility after `reset`).
7. List the policy under `evaluation.policies` in the configuration you want
   to evaluate it with.

## How results are organised

```
results/<config>/
    training/lr_<lr>_seed_<seed>/
        run_config.json        arguments and environment config of the run
        progress.csv           one row per RLlib iteration (episode_reward_mean, cur_lr, ...)
        episodes.csv           one row per training episode
        checkpoints/           periodic RLlib checkpoints
        checkpoint/            final RLlib checkpoint
        final_checkpoint.txt   path of the final checkpoint
    <scenario>/
        episodes.csv           one row per (policy, seed) evaluation episode
        steps.parquet          one row per environment step
    price_paths_4h.parquet, price_paths_30min.parquet   (Figure 3 inputs)
```

`results/` and `figures/` are git-ignored (see `.gitignore`); produce them
with `make train`, `make evaluate-baselines`, `make evaluate-rl`,
`make price-paths` and `make figures`. The evaluation script replaces the rows
of a (policy, seed) pair that is re-run and appends new ones.

Do not commit anything under `logs/` or `ray_results/`.

## Changes to the MDP

Every change to the Markov decision process or to the market it runs in must
be recorded in `docs/CHANGES.md` before the pull request is merged. This
covers the state vector, the action mapping, the reward (weights `alpha`,
`beta`, `is_weight`, the definition of depth consumed `d_t`), the arrival
price, the execution window and start time, the time step, the background
configuration (number and parameters of agents, oracle, market-maker
wake-up frequency) and the evaluation protocol (seeds, number of windows,
statistics). The entry must state what changed, why, which decision of
`docs/CHANGES.md` (D1-D16) it supersedes or refines, and which results directories
were produced before and after the change.

Bug fixes that do not change trajectories (verified on at least three seeds,
as in decision D9) can be noted briefly; anything that changes a trajectory
needs a full entry.

## Pull request checklist

* `python -m pytest tests -q` passes locally.
* Code is black-formatted, typed and documented.
* New configuration files, policies or environment arguments are covered by a
  test and described in the relevant section of `DEVELOPER-GUIDE.md`.
* MDP or protocol changes are recorded in `docs/CHANGES.md`.
* No run outputs (`results/`, `figures/`, `logs/`) are committed.
* Commit messages describe the intent of the change, not only its content.

## Reporting problems

Open an issue with the configuration file, the command line, the seed and the
exact package versions (`pip freeze`). For discrepancies with the paper, quote
the table or figure and the value you obtained; the per-step versus
per-episode definition of the implementation shortfall (see `docs/DESIGN.md`)
is a frequent source of confusion.
